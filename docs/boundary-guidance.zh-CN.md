# 边界库的使用与发布提醒

**中文** · [English](boundary-guidance.md)

这份文档写给使用本 crate 的人：一个边界库在**极密集调用**和**被逆向**这两种真实压力下会怎样，以及建议怎么做。第零节是发布物的硬规则，任何要把实现交付出去的人应当先读它。

文中每个数字都注明来源。凡是"没测"的地方，文中会直接写明没测。

---

## 零、发布物红线（先读这一节）

本 crate 的存在理由之一是：**把实现以二进制交付，而不交出源码**。这条理由只有在发布物选对时才成立。下面是硬规则，不是建议。

### 0.1 三条规则

1. **对外只发动态库**：Windows 的 `.dll`、Linux 的 `.so`、macOS 的 `.dylib`。
2. **永远不发 `rlib`、`.rmeta`、`.pdb`、`.d`。**
3. **打包时按文件名选，不要按目录选。** 不要 `Compress-Archive` 整个 `target/release`。

### 0.2 为什么 `rlib` 等于交出源码

`rlib` 里装着 `.rmeta`，它是跨 crate 内联与 rustdoc 的输入，保存的是**源码级信息**，不是机器码。实测（同一组四条本仓文档注释原句做探针）：

| 产物 | 文档注释命中 | 体积 |
| --- | --- | --- |
| `xt_kernel_dynlib.dll`（交付物） | **0 / 4** | 275,968 B |
| `libxt_kernel_impl-*.rlib`（实现） | 1 / 4 | 278,726 B |
| `libxt_kernel-*.rlib`（内核） | 2 / 4 | 785,382 B |

`rlib` 里能直接读出 crate 文档的完整句子，例如：

```
The map is the working form; [`TermStats::top`] produces the ordered form a
This crate is an ordinary Rust library: it knows nothing about stable
layouts, dynamic libraries or the ABI crate in this workspace. It exists to
```

这些文字比反编译产物好读得多——它们本来就是写给人看的设计说明。反编译需要成本，`strings` 不需要。

### 0.3 每个文件的处置

| 文件 | 能否发布 | 说明 |
| --- | --- | --- |
| `xt_kernel_dynlib.dll` / `.so` / `.dylib` | **可以** | 唯一必须发布的文件 |
| `xt_kernel_dynlib.dll.lib` / `.exp`（MSVC 导入库） | 可以，按需 | 只含两个导出名：`xt_kernel_entry`、`xt_kernel_shutdowns`；给 C/C++ 宿主链接时用 |
| `*.pdb` | **不可以** | 实测 1,249,280 B，含全量 Rust 符号名（`KernelWorkspace`、`top_terms` 等） |
| `*.rlib` | **不可以** | 见 0.2 |
| `*.rmeta` | **不可以** | 文档注释的载体 |
| `*.d` | 不可以 | 构建期依赖清单 |

### 0.4 最容易犯的那个错：压 `target/`

从干净目录执行一次 `cargo build --release --workspace` 之后，本仓 `target/release/` 里有 **12 个 `.rlib`（合计 6.47 MB）、6 个 `.rmeta`、12 个 `.pdb`、24 个 `.d`**。它们不是"顺便产生的东西"——那是各个 crate 的编译产物，其中就包括需要保密的实现。

所以规则 3 不是洁癖：**按目录打包，等于把要保密的东西一起发出去**，而被发出去的文件名里没有一个写着"源码"。

同一个构建里，交付 crate 自己一个 `.rlib` 也没有（实测 0 个）——这是 0.5 那个拆分带来的效果。

### 0.5 结构上的注意点：`crate-type` 里带 `rlib` 的 crate 不能当交付单元

本仓早期版本里，`demo/dynlib` 是 `crate-type = ["cdylib", "rlib"]`，因为有一个对照程序要链接它。这正是要避免的形状：交付 crate 同时产出 rlib，那么误打包就会把它自己的 `.rmeta` 一起发出去。

现在本仓按下面的形状拆分，可以直接照搬：

| crate | 产出 | 角色 |
| --- | --- | --- |
| `demo/impl`（`xt_kernel_impl`） | `rlib` | 实现本体，给需要链接形态的人 |
| `demo/dynlib`（`xt_kernel_dynlib`） | **只有** `cdylib` | 交付物：导出两个名字，不含自己的代码 |

结论：

- **交付单元必须是只产出 `cdylib` 的那个 crate。** 如果实现和导出写在一个 crate 里，拆成两个：实现放进 rlib crate，交付 crate 只做转发并声明 `crate-type = ["cdylib"]`。
- **`cargo publish` 不能用。** 发布 crate = 公开源码。本仓 `demo/` 下全部 crate 都是 `publish = false`，实测 `cargo publish --dry-run -p xt_kernel` 返回 101 与 `` `xt_kernel` cannot be published ``。

### 0.6 发布前用一条命令验证

在打包目录上跑，期望输出是 **0 条**：

```powershell
Get-ChildItem -Recurse <打包目录> -Include *.rlib,*.rmeta,*.pdb,*.d | Select-Object FullName
```

Linux/macOS：

```sh
find <打包目录> -name '*.rlib' -o -name '*.rmeta' -o -name '*.pdb' -o -name '*.d'
```

这条命令在本仓实测过：对一次 `cargo build --release --workspace` 后的 `target/release` 运行返回 **54 条**；对一个只放了 `.dll` 的目录运行返回 **0 条**。所以它既能发现错误，也不会对正确的交付集误报。

再确认交付目录里只有动态库（和可选的导入库）：

```powershell
Get-ChildItem -Recurse <打包目录> | Select-Object Name
```

### 0.7 给在本仓做改动的人（含自动化代理）

- 不要为了让某个程序"能链接"就把交付 crate 的 `crate-type` 加上 `rlib`；要用链接形态做对照，就新建一个 rlib crate（本仓 `demo/impl` 就是那个 crate）。
- 本仓 `demo/dynlib` 只声明 `crate-type = ["cdylib"]`；向它加 `rlib` 会让交付物自带一份源码级元数据。
- 不要对 `demo/kernel`、`demo/impl`、`demo/dynlib` 或任何含实现的 crate 执行 `cargo package` / `cargo publish`。
- 不要把 `target/` 或 `tmp/` 放进压缩包、镜像或制品库。
- 不要把 `.pdb` 提交进仓库或发布。
- 需要证明"交付物里没有源码级信息"时，用 0.2 的探针方法重新跑一遍，不要凭印象。

### 0.8 宿主侧怎么接入（这条决定要不要交出源码）

同一个库有两种接入方式，只有一种与保密兼容：

| 接入方式 | 宿主需要什么 | 与保密兼容吗 |
| --- | --- | --- |
| 运行时加载（`xt_kernel_api::loader::Plugin::load`） | 一个 `.dll`/`.so`/`.dylib` | **兼容** |
| 链接期接入（`extern crate`、把 rlib 加进依赖） | 一个 `rlib` | **不兼容**：拿到 rlib 就等于拿到实现 |

所以当一个宿主方说"给我一个能直接链接的库"时，那个请求本身就是在要源码。正确回答是：用 `xt_kernel_api` 声明接口，用 `Plugin::load` 在运行期加载实现；如果你希望宿主自己也编译出可执行文件，它只需要 API crate，不需要实现 crate。

本仓的 `demo/app` 就是这种接入；`demo/static` 是例外，它链接 rlib 只是为了让"同一套协议"可以被对照验证，不是推荐的交付形态。

### 0.9 运行期卸载（换 mod、热重载）

进程不退出、卸掉一些库再加载别的库，这件事可行，但**顺序由宿主保证**。`Plugin` 丢弃时依次做三件事：放掉库交给宿主的对象、跑库自己的 shutdown 钩子、最后才 `FreeLibrary`/`dlclose`。宿主自己还要守四条：

1. **库分配过的每一个 owned 值**都必须在卸载前 drop —— 不只是根对象和从它上面拿到的会话、子对象，还包括任何一次调用**返回**的 owned 值：`StableString`、`StableVec`、`StableBox`、`AbiError`、`StableMap`……每一个都带着库自己的释放函数指针，drop 时要调它。宿主侧凡是「从库那里拿到的值」，都要活不过卸载点。
2. 库起的线程必须在它的 shutdown 钩子里 join 完；`FreeLibrary` 不等线程。
3. 你注册给库的回调要在卸载前撤销。
4. 卸载与"正在进入这个库"的调用之间没有任何同步，这是宿主的责任。

第 1 条为什么容易漏：`LoadedPlugin` 只释放 descriptor 里那几个字段（`name`、`api`），**它追踪不到**你从方法里拿到的那些值 —— 那些值的所有权已经在你手上了，宿主是唯一知道它们在哪的人。所以「宿主状态里的 owned 值」与「`LoadedPlugin`」之间必须有明确的 drop 先后，让前者先死：

```rust
// 宿主自己的一层，装所有从库那里拿到的值。
struct HostState {
    names: Vec<StableString>,
    last_error: Option<AbiError>,
    session: Option<LoadedPlugin>,
}

impl Drop for HostState {
    fn drop(&mut self) {
        // 这些值都带着库里的释放函数，先于 session 释放。
        self.names.clear();
        self.last_error = None;
        // session 最后 drop：它跑 shutdown 钩子，然后卸载库。
    }
}
```

换句话说：**别把库返回的 owned 值放在比 `LoadedPlugin` 活得更久的地方**（进程级 `static`、另一个线程的队列、比它早声明的同作用域变量都会这样）。`drop` 的顺序在同一作用域里是声明顺序的逆序，所以想省掉上面那层包装，就得自己把这个顺序摆对。

关于「让宿主不可能把库分配的值带过卸载点」的 lease/guard 机制：**本仓不加**。理由是这类值是一个**开放的集合**（任何 `AbiType` 都能是返回值），一个能持有它们的 guard 只能是对每个类型各生成一层包装，那等于在边界类型之上再造一层 ABI 类型，而它挡住的仍然只是「宿主主动把值存起来」这一种写法（值一旦被拆成字段、装进宿主的容器，guard 就管不到）。契约 + drop 顺序 + 上面那层包装是这份约束能做到的形态；真要机械地兜住，只有进程隔离这一条路。

还有一条是**库自己的事**：虚表按实现类型建一次、由所有该类型的值共享，所以它比任何值活得久，内存来自进程分配器，库卸载后没人能再释放它。库应当在自己的 shutdown 钩子里调用 `release_cached_tables()`（本仓 `demo/impl` 与 `plugins/abi_plugin` 的钩子都这么做）。

实测（本机，`demo/api/tests/unload.rs` 里的忽略测试）：不调用时每次加载/卸载留下约 480 B（2000 轮私有字节 +958 464）；调用后，同样按每批 2000 轮、共 10000 轮计量，净值为 0（单批出现过一次 20 KB 的台阶，随后被系统收回；计量精度是一个 4 KB 页面）。同一个测试还用 `GetModuleHandleW` 断言：drop 前模块在映射中，drop 后不在。

### 0.10 `validate` 校验的是「值自相一致」，不是「生产方可信」

`AbiType::validate` 会在安全代码读到值之前拒掉**值自己说矛盾**的那种情况：长度超过容量、tag 不是该类型定义的、地址不对齐、纳秒不小于一秒、表的槽位与声明不符。它拒不了另一种：**块本身没有那么大**。

```
length = capacity = 1_000_000，pointer → 1 字节的块
```

这个头部全部通过（长度没超过容量，字节数可寻址），然后 `validate` 逐元素读、`Drop` 按 1 MB 释放。校验器没有「这块实际多大」这个信息——`StableStr` / `StableSlice` 连 capacity 字段都没有。

所以在威胁模型里要写清楚：**`load` 是 `unsafe`，它要求你加载的库的代码本身可信**；`validate` 的作用是挡住「同一份声明在两端的实现或数据出了偏差」，不是「恶意插件进不来」。要让接收侧能扛恶意生产方，必须让协议把**接收方真正持有的字节数**传进来：本仓有四个构造点收这个参数（`available`）——`StableStr::from_raw_parts_checked`、`StableSlice::from_raw_parts_checked`、`StableSliceMut::from_raw_parts_checked`、`StableBox::from_raw_parts_checked`；它们只在**构造**时比对，访问器与 `StableVec`/`StableString` 的构造都相信值里的数字。这属于协议设计，不是校验器能补的一层。

反方向是同一件事：**宿主交给库的那份描述也有版本与布局**。`HostServices` 的 `size` 只说覆盖多少字节，`version` 说协议的语义，`layout_revision` 说每个字段在哪；库该看的是三样。`plugins/abi_plugin` 就是这么做的。只比 `size` 与 major 会漏掉「同一 major、同样大小、但字段被重排」这一种：那时 `size` 通过、major 通过，库按错误偏移读 `allocator`/`log`/`query`，再按读到的函数指针调用。

## 一、极密集的边界调用：百万级物体怎么处理

### 1.1 先看一次跨越边界要多少钱

同一份工作负载、同一台机器、release 构建，三条路径各跑三次，表中取每个场景的最小值（链接进来 = `demo/static`，运行时加载 = `demo/app`，参考 = `demo/native`）：

| 场景 | 直接调用 | 边界（链接进来） | 边界（运行时加载） |
| --- | --- | --- | --- |
| `split_fixed`，一个数字进、两个数字出，**不分配** | 0.5 ns | 6.7 ns | 6.7 ns |
| `classify`，一个数字进、一个字符串出 | 21.1 ns | 60.4 ns | 60.0 ns |
| `analyze`（缓存命中），一个字符串出 | 117.3 ns | 151.3 ns | 156.5 ns |
| `top_terms`，一次排序，两个 pair 出 | 425.8 ns | 564.3 ns | 603.9 ns |
| `tokens`，5 个字符串出 | 248.6 ns | 565.1 ns | 568.8 ns |
| `reachable`，两条边进、一个序列出 | 278.4 ns | 392.1 ns | 405.6 ns |
| `digest`，4 KiB 进、一个字符串出 | 9,142.9 ns | 9,260.9 ns | 9,113.8 ns |
| `session` 往返（四次调用） | 277.0 ns | 373.5 ns | 437.0 ns |

测量条件：Windows x86_64-msvc，默认 release 配置，`xt_kernel_dynlib.dll` 275,968 字节（本表测量时的构建）；同一配置在 2026-10-24 的构建是 293,888 字节，差异来自随后补入的容器方法、派生实现与稳定哈希，它们不在这几条调用路径上。每个场景先预热再计时一批，取整批的平均值，再在三批之间取最小值。返回的 owned 值在每轮结束时释放，所以数字里含释放成本，与真实使用一致。

#### 第一件要说清的事：链接进来不等于没有边界

"静态链接"这个词在这里只意味着**实现被链接进可执行文件**，不意味着调用变成了直接调用。三条路径实际做的事完全不同：

| 路径 | 调用形式 | 返回值 |
| --- | --- | --- |
| `xt_kernel_native` | 直接调用 `Engine::split_fixed` | Rust 的值 |
| `xt_kernel_static` / `xt_kernel_app` | 通过对象表里的函数指针调用 | 边界类型，由宿主的分配器构造 |

后两条路径**跑的是同一套协议**：查槽位、间接调用、把结果构造成 owned 边界值、校验。动态加载只多一件一次性的事——打开文件、查两个符号。所以两者每调用的成本必然相同，上表也确实是相同。**链接进来省下的是部署与启动，不是每次调用的延迟。**

#### 第二件要说清的事：钱花在"构造返回值"上

`split_fixed` 这一行是为此加的对照：它只做算术、不分配。它的边界成本是 **6.7 ns**，而直接调用几乎是 0。所以：

- **跨越边界本身：≤ 6.7 ns。** 这是"查槽位 + 间接调用 + 校验"的全部代价。
- **每个返回的 owned 值：约 30~40 ns。** `classify` 是 60.4 − 21.1 = **+39 ns**，`analyze` 是 **+34 ns**。原因是多了一次分配与一次复制：内核本来就产出一个 `String`（内核自己的分配），跨边界时还要按宿主的分配器再造一个拥有所有权的边界字符串，收尾再释放。
- **每个返回的字符串在批量里更贵。** `tokens` 五个字符串 +317 ns，平均约 63 ns/个（含容器增长与五次成对分配/释放）。
- **输入按字节收费，不是按元素。** 每个入参在边界处都会被读一遍：字符串要验 UTF-8，容器要验头部再逐个校验元素。成本与字节数成线性，本机实测（`tmp/validate_probe`，release，取三批最小值）校验一个 `StableStr` 的参数：1 KiB 21.1 ns、4 KiB 56.0 ns、64 KiB 983.7 ns、1 MiB 16.5 µs，约 15 ns/KiB。所以 `digest` 的 +118 ns 里，4 KiB 输入本身的校验（≈56 ns）约占一半，剩下的是构造返回值与噪声。`reachable` 的两条边很小，+114 ns 基本不是校验。
- **一次调用里的多次访问器会累加。** `session` 往返是四次调用，+97~160 ns。

所以成本模型是：**每次调用约 7 ns 的固定开销 + 每个返回的 owned 值一笔 30~40 ns + 输入输出按字节计的校验（约 15 ns/KiB）**。**不是**每个输入元素一笔——这条区别决定了下面的建议：批量传数据很便宜（每 MiB 约 16 µs），批量返回小容器很贵。

一个测量上的注意：给 `split_fixed` 喂恒定参数时，直接调用那一路会被优化器整个移出循环，量出来是 0.2 ns 的假数字。表里的数字来自每轮变化的参数。任何"边界 vs 直接"的对比都要先确认直接调用那一路没有被优化掉。

#### 查槽位不随方法数线性增长

表项在建表时按“方法标识符”排好序，所以超过 16 项的表找槽位是二分；16 项以内两种表都走线性扫描（分治的循环开销在那一段更贵），所以前三行量到的是表项落在哪个位置，不是两种算法的差别。手写的、没排序的表不走二分，从头逐个比；有序表的二分没命中就直接回答"没有"，不再补一轮扫描。

本机实测（release，取三批最小值，同一张表的最后一次查找，即二分的最坏位置）：

| 表长 | 有序表（>16 项走二分） | 未排序的表（一路扫描） |
| --- | --- | --- |
| 4 | 1.64 ns | 0.73 ns |
| 8 | 2.27 ns | 1.46 ns |
| 16 | 3.73 ns | 2.91 ns |
| 64 | 5.55 ns | 12.67 ns |
| 256 | 7.39 ns | 52.95 ns |
| 1024 | 9.34 ns | 193.82 ns |

所以对常见的小 trait（十来个方法）两者相差不到 1 ns；有 24 项以上开始反转，64 项时快一倍以上，1024 项时快约 20 倍。表的字节布局没有变（头、表项、哨兵），变的只是表项的先后顺序，而顺序不是协议的一部分：调用按标识符找表项，不按位置。

### 1.2 为什么"每个物体跨一次边界"不能靠优化救

用上表实测的数字算，而不是用一个悲观的常数：

```
只跨越、不返回 owned 值：10^6 × 6.7 ns = 6.7 ms      （60 fps 一帧 16.7 ms）
每次返回一个字符串：      10^6 × 60  ns = 60  ms      （已经超了 3.6 倍）
```

6.7 ms 这个数说明：**单纯"每次调用跨一次边界"并没有出局**，它占了 40% 的帧预算——很难看，但不是不可能。真正致命的是后面两条：

```
每次返回一个 owned 值：   再加 10^6 × 39 ns = 39 ms
数据本身：10^6 × 64 B = 64 MB / 帧，60 Hz 下约 3.8 GB/s
```

所以问题不是"边界够不够快"，而是两件事：

1. **返回值不该逐物体构造。** 一次调用返回 $N$ 个 owned 值，就付 $N$ 次分配与复制。这是可以消除的（批量化 + 宿主 arena）。
2. **数据量有物理上限。** 3.8 GB/s 是内存带宽量级的事，就算边界零成本也省不掉。

结论：性能在这里由**调用的形状**决定，单次开销的优化空间只有几纳秒。

### 1.3 职责在哪一层

| 层 | 该负责的 | 不该负责的 |
| --- | --- | --- |
| 本 crate（ABI 层） | 让批量**表达得出来**：借用切片零拷贝进、宿主提供的分配器接管出、形状稳定 | 调度、线程池、SIMD——那是算法与策略 |
| 你的 API 门面 | 把"每物体一次"折叠成"每批一次"；把 arena 分配器一路传下去 | 决定内核并行度 |
| 你的 kernel | 批量算法、SoA 布局、SIMD、并行 | 为边界特化数据结构 |
| 宿主程序 | 复用缓冲、控制分配器、控制调用频率 | 指望 ABI 层替它批量 |

### 1.4 建议顺序（按收益排）

**① 批量化。** 把 $N$ 次调用改成一次。参数用 `StableSlice::from_slice` —— 它**借用调用方的内存**，不复制、不分配，所以 `transform(StableSlice<Mat4>)` 这种形状今天就能写。你的矩阵类型只要是 `#[repr(C)]`，用 `unsafe_stable_element!` 声明一次即可（名字里的 `unsafe` 就是那条承诺：每一边的布局与偏移都相同）。

**② 宿主提供分配器。** 每次调用返回的容器用的是**宿主递进来的** allocator，不是库自己的：

```rust
let arena = AbiAllocator::from_parts(arena_ptr, allocate, deallocate, reallocate);
let host = HostServices::new(arena);
```

于是库里的每一次分配都变成 arena 的 bump，**一帧末尾整体回收**，调用之间没有 `free`。这条路径已经是现成的，缺的只是示例——如果你在做这件事，先按这个形状写，不要先改 crate。

**③ 复用对象，不要每帧重建。** 打开 session、解析描述符、adoption 都只在启动时做一次。`Plugin::load` 返回的对象应当在整个运行期存活。

**④ 让热点返回标量或句柄，不要返回小容器。** 每个返回的 owned 值约 30~40 ns（一次额外分配 + 一次复制），而跨越本身只有 7 ns。需要批量结果时，一次返回整个序列，而不是 $N$ 次各返回一个。

**⑤ 把循环搬进库里。** 如果某个操作天生"每个物体都要问一次"，那就让库自己循环：宿主跨一次边界，库内部遍历 $N$ 次。边界适合传数据，不适合传控制节奏。

**⑥ 别把"链接进来"当成性能手段。** 它省的是部署与启动（一个文件、一次符号查找），不是每次调用。想让每调用接近 native，只有 ①/②/⑤。

### 1.5 已知限制（按当前实现实测）

说清楚，免得你按不存在的形状设计：

- **可写借用是一次调用的借用。** `StableSliceMut<'a, T>` 能让实现就地把你的缓冲改掉（`tests/objects.rs` 的 `a_method_can_write_through_the_storage_it_was_given` 走的就是这条路）。但 `'a` 由调用方给出，编译器不允许实现把它存进自己的字段：句柄只在这次调用里有效。
- **拥有存储的边界值不是 `Send`/`Sync`。** 它带着构造它的那套分配器函数与上下文，crate 无法证明另一端接受跨线程调用。多线程的正确形状是**每线程一个句柄**（或每线程一次加载），不要跨线程传递同一个对象。不含分配器的值（借用的视图 `StableStr`、`StableSlice`、`StableSliceMut`、`StableOsStr`、`StablePath`，以及 `StableArray`、元组、`StableDuration`、`AbiVersion`、`Handle`、时间值）由编译器按成员自动判定：它们通常就是 `Send + Sync`，因为它们只带自己的那几部分。**Cow 是这条规则的一个反例**：`StableCowStr` / `StableCowSlice` 的两个字段按布局都存在，未激活的那个仍是一整个 `StableString` / `StableVec`，所以即使是 `borrowed` 形态也不是 `Send`——这是布局固定的代价，不是遗漏；要跨线程就在那一侧 `into_owned` 之后按 owned 值的规则处理。
- **查槽位有开销，但可以摊薄。** 生成的表在建表时按标识符排序，超过 16 项的表走二分；16 项以内以及手写的、未排序的表走线性扫描。一次调用里这点开销可以忽略，所以先批量，不要先去改查找。
- **每个返回值都会完整校验一遍**，然后才交给安全代码：字符串整段查 UTF-8，容器逐个元素查，对象查表头与地址。所以一次批量返回要**再遍历一遍结果**；这笔成本与"每调用固定开销"是两笔账，大返回值上它才显出来。元素类型本身没有内容要查时（`u8`、`u64` 这类），release 下逐元素循环会被整个优化掉：实测 `StableSlice<u64>` 的 `validate` 从 1 个元素到 1,048,576 个元素都是约 4.3–4.4 ns/次，与长度无关。所以"按字节收费"这句话对字符串成立，对纯数字切片不成立。
- **参数也会被完整校验，只是校验的一侧不同。** `stable_object!` 生成的访问器在**发送侧**逐个校验参数：不合法就把该参数丢弃并 panic（那张表没有状态字可以上报）。`stable_object_guarded!` 生成的表在 **trampoline 里（接收侧）**校验参数，不合法就拦下、回报 `AbiStatus::InvalidArgument`，实现不会被执行。所以参数的成本与返回值同源：两端互不信任时用守卫式声明，用它与不用它都逃不过参数的那一遍遍历（区别只在由谁查、失败时怎么报）。
- **每传或每收一个对象句柄，都要把它和接收方的声明比一遍。** `validate_handle` 先查表头，再比较方法集合。表项数与声明相同、表头合并签名也相同时，仍然要按声明里的每个槽位标识符在表里找一次（表是有序的，所以是二分；手写的未排序表走线性扫描）——合并签名是列表的 64 位摘要，不是列表本身。只有「对端声明少几个方法」或「多几个方法」这种真正的修订关系才逐项判断，而那一路是**每个表项对声明做一次查找**：方法数 1024 的 trait、两端版本又不一致时，一次句柄传递约 100 万次比较。常见 trait 只有几个方法，可以忽略；但这是每次传句柄都发生的，不只是 adoption。
- **排序的临时缓冲走值自己的分配器**（不是进程分配器），所以 arena 的"帧末整体回收"在排序上也成立；代价是排序失败会返回错误而不是 panic（fallible 入口）或 panic（`sort`/`sort_by`）。稳定排序天然需要与向量等大的临时块（峰值 2×），要避免它就用 `sort_unstable_by`：堆排序只在向量自己的块内交换，**不分配**，因此也没有 fallible 形式；代价是相等元素的相对顺序不再保留。
- **对象构造期只有第一次注册要拿进程级锁**，每个 trait 一张表。实现类型首次注册时持锁建表，并把一份不可变的条目副本发布出去；之后同类对象的构造只读那份副本，不加锁。所以热路径上反复构造同类对象不会互相等待，但多线程同时**首次**构造同类对象会串行一次。代价是**每次发布都整体复制条目并保留上一份**（正在读旧副本的线程仍然要能读完），所以同一个 trait 保留的条目数是 `N(N+1)/2`（N = 该 trait 在本进程里注册过的实现类型数；每条 24 字节：一个类型标识和一个表地址）。N=100 约 120 KB，N=1000 约 12 MB。它只随**实现类型数**增长，不随构造次数增长，且 `release_cached_tables()` 在卸载时整条链一起归还；N 在进程内由代码决定，通常是一次性开销。要让旧副本更早释放，就得让每个读者宣告「我正在读」，而那是一次所有线程共享缓存行的读改写——正是这套无锁读想避开的开销，所以这里选择保留链并写明它的形状。
- **零尺寸元素的长度没有任何上界，所以边界对它是拒绝的。** `StableVec<()>` 这类容器不占缓冲，它的 `length` 无法由容量推出：对端写一个「长度 2⁶³」的头部就通过全部头部检查，而接收侧的 `validate` 要按长度走一遍。`StableVec`/`StableSlice`/`StableSliceMut`/`StableMap`/`StableSet` 的 `validate` 因此拒绝「零尺寸元素 + 非零长度」——这种容器除了那个数什么也没带，任何字节数、对齐、地址都不能说明它是真的，而本库也不会替调用方发明一个上限（任何具体数字都是臆断，不是这条协议的属性）。「头部检查」`validate_header` 仍然接受它，因为同一个函数也决定「这个值能不能被本进程释放」，而本地构造的零尺寸容器里的元素析构仍然要跑。发送方手里若只有一件事要说，就把那个数当作数字发出去。接收侧若要在自己的入口上另设额度，`from_raw_parts_checked` 的 `available` 只作用于构造，不作用于访问器。
- **哈希容器只有拿到同一个哈希函数才能用。** 条目身份是 `(hash, key)`，上下文的 `validate` 只看这两者对是否严格递增、元素是否合法，**不重算哈希**——接收侧手上没有那个函数。所以发送方用 A、接收方用 B 时，值会通过 `AbiType::validate`，然后每一次 `get` 都 miss。两条出路：①函数由调用方给（`insert(hash, …)`），接收侧知道该用哪个函数时用 `validate_with` 在读取前查一遍；②函数由本库给——`StableHash` 把编号方式固定在本库内（FNV-1a、按宽度与字节序编码，`usize`/`isize` 因为宽度随目标而**不**在内），用 `insert_stable` 建的表可以被 `validate_stable` 单独核对，两端不需要先约定任何东西。把哈希函数的**标识**放进值里不解决问题：两端仍然要对「同一个函数」达成一致，多存一个数只是把同一个约定换个地方写；而由本库计算的那个数是可以被核对的，因为它不依赖任何一方。

### 1.6 怎么自己量化

`demo/` 里的三个程序就是量具：同一个场景、同一份期望答案，三种到达方式。改内核后重跑三条，用差值而不是绝对值判断边界成本。绝对数字会随机器、编译器版本、优化等级漂移。

## 二、动态库被逆向时，代码能保护到什么程度

### 2.1 先把天花板说清楚

发布出去的原生代码就是信息。反汇编能拿到控制流、常量、数据布局；反编译器能把它们还原成可读结构。**没有任何手段能让二进制里的算法不泄露**，只有"提高阅读成本"。所以有意义的问题不是"能不能藏住"，而是"我们是不是白送了东西"。

下面这些是**本仓实测**的结果，不是推测。

### 2.2 曾经白送、现在已修：完整的方法签名表

修复前的 release DLL 的 `.rdata` 里是明文：

```
analyze (shared guarded), StableStr<'_> -> StableString;tokens (shared guarded), ...
... open_session (shared guarded), StableStr<'_> -> SessionObject;add (mutable guarded), ...
```

每个方法的名字、参数类型、返回类型、接收者种类全在里面——等于附了一张接口地图。

原因不是设计，是实现：签名哈希当时在表构造时用 `declaration_id(stringify!(...))` 求值，而表是**运行期**建的，所以那串文字必须作为数据存在。表里真正需要的只有 `u64`，文字只是算哈希的原料。

现在这条求值在编译期完成，而且标识符已经不再由文字算出：每个边界类型有一个数（`AbiIdentity::IDENTIFIER`），一个方法的标识符由它提到的那些类型的数折叠而成。所以**签名**没有可供还原的文本，任何优化等级下都是如此。

**这句话只覆盖"没有明文"。** 折叠是无盐的，而折叠算法本身是公开协议（手写表必须照着实现），所以拿到二进制的人可以枚举候选的方法名与参数类型组合，算出 `slot_id` 去和表项里的 8 字节比对；trait 名同理（`declaration_id(name)` 就是无盐 FNV）。这不是"能执行代码"，而是"接口地图可以离线重建"，只是多一道枚举成本。要挡住它得让数字里带上双方共享的盐，那要求两端同源构建；或者干脆由调用方给一个不透明的标识（`abi_try_from_value_with` 已经收这个参数；同一个实现类型在一个进程里只能对应一个标识，换第二个会 panic）。本仓不做这两件事，因为没有双方共享的秘密可放。

修好这一项那一轮的实测（两个体积是同一次配置下的前 / 后）：

| | 修复前 | 那一轮修复后 |
| --- | --- | --- |
| `xt_kernel_dynlib.dll` 体积 | 278,528 B | 281,088 B |
| 签名文本（`shared guarded`、`StableStr<`、`top_terms`） | 明文可见 | 逐串搜索均为 false |

体积随二进制内容变化，不是常量：2026-10-24 同一配置的构建是 293,888 字节。三条演示路径在同一次构建下全部通过（原生 33 项、静态 37 项、动态 37 项，0 失败），说明两端围绕同一份声明算出的槽位标识符仍然逐一对应。数字来自类型的声明本身：同一个类型无论写成 `StableStr`、`StableStr<'_>` 还是带路径的全名，得到的是同一个数；换一种写法的别名也落在同一个数上。

**表头的 `type_id` 是另一件事。** 它来自 trait 的名字（`type_id_of(stringify!(Trait))`），折叠在编译期完成，但那个字面量仍然是这次调用的输入。实测：release 的同名 DLL 里搜不到 trait 名，**debug 构建里可以**（`Child`、`Session`、`Workspace` 三个常量相邻躺在 `.rdata` 里）。所以"trait 名不会出现在二进制里"只在优化构建下成立；要连 debug 也不带，得给 trait 一个手写的数字标识，不要再让名字参与。

### 2.3 仍然会泄露的部分（实测仍在）

| 内容 | 例子 | 来源 | 稳定 Rust 能否去掉 |
| --- | --- | --- | --- |
| panic 里的文件名与行号 | `demo\kernel\src\engine.rs` | `panic!` 的位置信息 | 不能（nightly 有 `-Zlocation-detail=none`，本仓未验证） |
| 断言与错误文案 | `cannot be measured that way`、`the cache was not poisoned` | 你的实现 | 能，但要你自己改文案 |
| 方法名（诊断用） | `the object does not declare the method` | 本 crate 的诊断 | 能，但会损失报错质量 |
| 全量符号名 | `KernelWorkspace`、`top_terms` | **PDB 文件** | 能：不发 PDB |
| 分配器、日志、query 的函数地址 | 每个 owned 值头部的四个指针 | 值是 `AbiAllocator` 的一部分 | 不能，但它只是本进程的地址，不是代码内容 |

关于最后一行：**任何给出去的 owned 值都带着你的分配器函数与上下文的地址**（`StableString`、`StableVec`、`StableBox`、`StableDyn` 的头部都是；`StableCowStr::borrowed` 里那个未激活的 `owned` 字段也带着一份）。`Debug` 刻意不打印这些地址，但**线缆上的字节会带**。它们泄露的是本进程的内存布局，不是实现；如果这一点也不能接受，就别把 owned 值送给不受信任的一方，改用借用视图（它们只带指针与长度）。

守卫式声明在 panic 时**不把 payload 送过边界**：trampoline 只写一个状态字，调用方读到的是 `AbiStatus::Panic`。手写的入口如果用了 `unwind::guarded`，那它会复制最多 4096 字节的 panic 消息过边界，这由写那个入口的人决定。有一处例外要单独说：参数校验就是跑参数类型自己的 `validate`，它在 trampoline 里 panic 时实现还没被执行、接收者的值也还没搬出去，所以这条路上报的是 `AbiStatus::InvalidArgument`，句柄照常释放自己持有的那份值。

两点实测结论值得记住：

- **`strip = "symbols"` 在 MSVC 目标上对本 DLL 无效**：体积一点没变（275,968 B → 275,968 B），PDB 照常生成。别把它当成保护手段。
- **`llvm-strip --strip-all` 同样无效**：这个 PE 没有可剥的符号表，剥完大小不变。真正把符号名带出去的是**旁边的 `.pdb`**（实测 1,249,280 B）。部署时不要发它。

### 2.4 不破坏 ABI 的混淆手段

先说原理：**稳定 ABI 只约束边界上的东西**——导出的入口符号、描述符协议、发布类型的布局、槽位哈希的算法。它**不约束库的内部实现**。所以绝大多数混淆手段在原理上都与 ABI 兼容，只要触碰不到那四样。

| 手段 | 对 ABI | 对性能 | 说明 |
| --- | --- | --- | --- |
| `lto = "fat"`、`codegen-units = 1` | 无影响 | 未在本仓做前后对比 | 跨 crate 内联，抹掉大部分函数边界；对逆向的阻碍是这几项里最大的，代价只是编译变慢 |
| 不发 PDB、符号外置 | 无影响 | 无 | 性价比最高的一条 |
| 脱敏 panic/断言文案 | 无影响 | 无 | 文案会泄露模块结构（见 2.3） |
| 字符串加密 | 无影响 | 有（解密开销） | 值得做的是"密钥/授权判定"这类字符串，别全局开 |
| 控制流平坦化、虚假控制流 | 无影响 | 10%~100%+ | 需要 LLVM 插件；只对**非热点**模块开，热点模块保持可优化 |
| 按客户构建（不同 seed / 不同裁剪） | 无影响 | 无 | ABI 不变，宿主编译一次，换库不用重编——这是稳定 ABI 对保密的**正面价值** |
| 加壳、虚拟化保护 | **风险高** | 很大 | 与动态加载、内存属性、签名校验冲突；不建议用于 `cdylib` |

### 2.5 "既不改 ABI、又不掉性能、还能混淆"——能到什么程度

分三段回答，因为这三件事的耦合程度不同：

**不改 ABI：可以，而且是常态。** 上表前六项都不触碰边界。只要入口符号、描述符协议、发布类型布局和槽位哈希算法不变，宿主一行都不用改。

**不掉性能：只在"低成本档"成立。** LTO、单 codegen unit、不发符号、文案脱敏、按客户构建——这几项都不往热点里加指令（LTO 的前后差异本仓未测）。它们同时也是**最有效的**：因为混淆的价值在于让"读的人"迷路，而内联 + 无符号已经消灭了大部分可读结构。

**强混淆 + 零性能损失：不成立。** 控制流平坦化和虚拟化本质上是往每条路径里加指令，两者直接对立。要保密就得在热点之外付这笔钱。

还有一条硬冲突必须写出来：**`panic = "abort"` 与守卫宏互斥**。库内 panic 的隔离依赖 `catch_unwind`，而 `catch_unwind` 需要栈展开。开了 abort，库内一次 panic 直接终止宿主进程，隔离语义消失。不要为了"更难逆向"顺手开它。

### 2.6 如果威胁是"别人改一改说是自己的"

这一节针对的威胁和前面不同：不是"别人读懂我的算法"，而是"别人拿到整套代码，改一改就当成自己的产品"。两者的手段差别很大，混在一起谈会选错工具。

**先分清两种到手方式**：

| 方式 | 对方手里有什么 | 技术手段能否阻止 |
| --- | --- | --- |
| A. 源码到手（泄露、外包、离职、误发布、`cargo publish`） | 你的全部源码与注释 | **不能**。技术只能做到"不给出去""能证明你先有""能追溯到谁泄的" |
| B. 只有二进制 | 机器码 | 能提高成本，同样不能阻止 |

冒名风险主要来自 A。所以重点不在混淆，而在**发布物里到底装了什么**。发布物的硬规则与实测数据在第零节（0.2 到 0.6），这里只保留判断：`cdylib` 里没有本 crate 的文档注释，`rlib` 里有，因此**交付只发动态库**。

这条规则解释了本仓四层结构的实际价值：**"对外发布的"与"要保密的"被切成了不同的 crate**。`xt_kernel_api` 可以随宿主一起开源，`xt_kernel` 只以二进制出现，两者之间是稳定 ABI。

#### 对 A（源码到手）能做的四件事

1. **不发源码，也不发 rlib。** 私有 registry 或直接给二进制；`cargo publish` 发布的是源码，不要用它分发 kernel。
2. **缩小源码接触面。** 仓库权限、CI 日志、外包范围只到 API crate；示例与基准不要复制一份实现（`demo/bench` 里只有输入与期望值，没有算法）。
3. **证明"你先有"。** 发布物签名并登记哈希（可用第三方时间戳）。法律上这类证据比任何混淆都值钱。
4. **合同与许可。** 对"改一改说是自己的"，这是唯一有直接效力的手段：著作权归属、保密条款、禁止反向与再分发。技术措施的作用是让违约可被发现，而不是替代合同。

#### 对 B（只有二进制）能做的两件事

1. **每客户构建指纹。** 在 `capabilities()` 这类**冷路径**里嵌入一个构建标识（客户编号 + 构建时间 + 源码提交号）。热路径零成本，ABI 不变，因为它只是字符串数据。它能回答"这份 DLL 是从谁那里流出的"，但**不能**阻止对方重新编译。
2. **LTO + 单 codegen unit。** 让反编译产物离"能维护的代码"更远。这是唯一同时不损性能的一项。

#### 一句诚实的边界

**源码一旦离开你的构建机，技术上就拦不住"改一改"。** 技术能做的只有三件事：不给出去、能追溯、能证明先后。任何声称能"防住复制"的方案，都在卖第四件事。

如果你需要的是"即使代码在他手上也没用"，那只有三条路：算法放服务端、绑硬件、或接受"提高成本而不是防止泄露"。

稳定 ABI 在这里是助力：它让你可以把同一个实现分发给不同客户、随时整体替换、按客户定制构建，而宿主不必重编。**用可替换性换保密性，比藏代码可靠。**

### 2.7 擦除能擦到什么程度

`Wipe` 覆盖的是**内容**，不是**描述**：

- 一个 `StableString` 被擦后，字符的字节块清零了，但它自己的头部（地址、长度、容量、分配器）仍在原来的位置——因为值擦完之后还要用它去释放那个块，擦掉头部就等于把块泄漏掉。
- 容器的 `wipe_in_place` 会擦元素，也会擦**已经不在长度内的槽位**（`truncate`/`clear` 之后留在块里的内容）。哈希 map/set 走的是同一段代码，所以也覆盖多余容量；每个活动条目另外会把**存它的那个 64 位哈希值**一起清零，因为那个数是键的函数，留着它等于留着键的指纹。
- `StableOption::take` 移走值之后，字节仍在槽里（与 `truncate` 同一个策略）；此时 `wipe_in_place` 会直接清零载荷存储，所以「先 take 再 wipe」能把残留抹掉。
- 一个 `StableDyn` 被擦后，它占的那块内存清零了，但**析构函数在运行过程中释放的嵌套分配不会被擦**：实现里如果有 `String`/`Vec`，那些块是它在自己的析构里交还给分配器的，本仓拿不到它们的地址，也就写不进去。要连这些一起擦，只能由实现自己在析构里擦（或者让值实现 `Wipe` 并由持有方先调它）。
- 被释放的块里只剩"曾经有个块、多长、谁分配的"这类信息，不含内容。

所以对"密钥/令牌"这类数据：擦除是有效的；对"整个值曾经长什么样"这种要求，只能由持有存储的一侧（它知道块在哪里）在释放时一并处理。

还有两处会留下指纹、但不含内容，需要你自己判断要不要接受：

- `Debug` 对表头与对象打印 `type_id` 与 `signature`，它们是 trait 名与方法表的 FNV 哈希。名字本身没有出现，但一个指纹足以对候选名字做字典比对。日志如果要发给不受信任的一方，就别打印这两个值。
- `AbiError::Display` 打印消息原文。本仓的示例库现在只把**错误的种类**送过边界（`the graph has a cycle`），不再把内核自己的句子（含计数、偏移）送出去——错误是会被写进日志的那一种值。宿主若把 `Display` 直接写进自己的日志，等于把库写的任意文本带出进程边界；要控制这条路径，就在跨过边界处只转交 `status()`。

## 四、不能写进声明的形状

`stable_object!` 与 `stable_object_guarded!` 只接受一种槽位形状，其余形状在**声明处**就编译报错，不会等到第一次调用。这一节把每条拒绝、它的报错原文和替代写法放在一起。

### 4.1 一张表只列一个 trait 的方法

```rust
pub trait Store: Send { /* ... */ }
// error: a table lists the methods of one trait, so a declaration cannot name a supertrait
```

继承来的方法属于另一个声明，这张表里没有它的槽位。两种改法：把继承的方法在本 trait 里重新写一遍；或者把对象声明放在持有那些方法的 trait 上，让表列全。

### 4.2 接收者只有三种写法

支持 `fn name(&self)`、`fn name(&mut self)`、`fn name(self)`，后面是逗号分隔的 `参数: 类型`，可选返回类型，以 `;` 或默认实现结束。其余形状报 `a table slot has a fixed parameter list`：

| 写法 | 为什么不行 | 怎么改 |
| --- | --- | --- |
| 关联常量、关联类型 | 不是一次调用 | 放到普通类型上 |
| 没有接收者的关联函数 | 表按接收者分派 | 改成 `&self`，或用普通函数 |
| 泛型方法 `fn f<T>(...)` | 一个槽位只有一个参数表 | 每个实例化写一个具体方法，转发到实现里的泛型方法 |
| `-> Self` | `Self` 是实现类型，调用方不知道它 | 返回具体的边界类型 |
| 返回借用 | 槽位只为这次调用出借它的值 | 返回 owned 值，或让调用方传入它自己保留的存储 |

### 4.3 返回类型必须是 owned 值

返回类型里出现 `'` 报 `a method's return type names a lifetime`；写成最短形式的借用类型（`StableStr`、`StableSlice<u8>`、`StableSliceMut<u8>`、`StableCowStr`、`StableCowSlice<u8>`、`StableOsStr`、`StablePath`，带路径前缀也一样）报 `a method cannot return a borrowed type`。两种判定的区别只是写法，理由相同：调用结束后槽位不再拥有那块存储。`'static` 同样被拒——动态库里的"静态"数据在**卸载后**就没了，而类型系统不知道卸载这件事，所以 `StableCowStr<'static>` 这类可以装 owned 值的写法也写不出来；要返回它的 owned 形态，返回 `StableString`。

### 4.4 参数与返回值的类型必须是边界类型

两边都要实现 `AbiType`，所以 `String`、`&str`、`usize`、`bool` 这类类型写进声明会得到普通的 trait bound 错误。换成 `StableString`、`StableStr`、`u64`、`StableBool` 即可。

签名还要求两边实现 `AbiIdentity`：每个槽位记的是这些类型各自的数，而不是它们的写法。一个自己写的边界类型要补上这条（`unsafe_stable_identity!(Type);`，名字里的 `unsafe` 就是「两边对同一个名字的含义一致」这条承诺），否则声明会在 `AbiIdentity` 未满足处报错——`stable_enum!` 生成的类型已经自带实现。

### 4.5 一张表最多 1024 个方法

超过时在编译期断言失败：`a declaration has more methods than a table can record`。接收方最多读 `MAX_SLOTS`（1024）个表项，所以再往后列的方法没有任何对端能看见。

### 4.6 方法上的属性

属性分两类，宏按“它能不能落在那个位置上”来放：

| 属性 | 落在哪 | 效果 |
| --- | --- | --- |
| `#[cfg(...)]` | 表字段、槽位数组元素、访问器、跳板 | 被它们去掉的方法不产生表项，`ABI_SLOT_SIGNATURES` 也随之少一项（`tests/conditional.rs` 钉住这一点） |
| `#[cfg_attr(...)]` | 只落在生成的函数（访问器、跳板） | 它可能展开成字段不接受的东西（`#[inline]`），所以宏不往字段上放；要让方法在一个条件下消失就写 `#[cfg]` |
| 其余属性（`#[inline]`、`#[cold]`、`#[must_use]`…）与文档注释 | 只落在生成的函数（访问器、跳板）上 | 字段与数组元素不接受它们，所以宏不往那里放 |

这条分桶是把“属性决定方法存不存在”和“属性只影响函数”分开：前者必须每个位置都有（否则字段与表项对不上），后者放了只会在错误的位置报错。`tests/objects.rs` 的 `a_method_may_carry_an_attribute_that_only_a_function_accepts` 钉住 `#[inline]`。

写在 `struct` / `trait` / `enum` 自己的属性列表里的东西只作用于**那条声明**，宏生成的表、impl 与访问器不在其中。所以整条声明要门控时，属性放在**宏调用**上（`#[cfg(...)] stable_object! { … }`，这是合法的），不要写进声明内部——否则生成的表会去引用一个已被去掉的类型。

接收者可以写成 `&self`、`&mut self`、`self`，也可以写成 `self: &Self`、`self: &mut Self`（`tests/objects.rs` 的 `the_receiver_and_the_argument_list_may_be_written_out` 钉住后两种）。参数表可以以逗号结尾（`fn f(&self, a: u32,)`），四种接收者写法在两张表（`stable_object!` 与 `stable_object_guarded!`）上都如此。**唯一不支持的写法**：`&'a self`——它唯一的用处是返回借用，而带生命周期的返回类型正是本库拒绝的东西。

### 4.7 枚举声明的限制

`stable_enum!` 写出来的是一个 tag 加一个联合体，因此：

| 限制 | 原因 | 替代写法 |
| --- | --- | --- |
| 载荷不能带声明引入的生命周期 | 生成的类型没有生命周期参数，所以只有 `'static` 的载荷写得下去 | 用 owned 类型（`StableString` 而不是 `StableStr<'a>`）；`StableStr<'static>` 可以用 |
| 一个载荷最多 12 个字段 | 两个以上字段的存储形式必须是本库写出来的 `#[repr(C)]` 结构（`Payload2`…`Payload12`）：Rust 元组的布局由编译器决定，换个构建就可能换偏移 | 把字段收进一个边界结构体 |
| `stable_enum!` 要求载荷实现 `Wipe` | 它生成的 `Wipe` 逐元素擦除，且擦除后值仍要可释放 | 载荷不能擦除时改用 `stable_enum_unwiped!`：同一个类型，只是不带 `Wipe` |
| 判别值必须互不相同 | 两条臂会读到同一份载荷 | 编译期断言会拒绝重复（`a declaration names one discriminant twice`） |
| 比较、复制、哈希与默认值要显式点名 | 一个 `derive` 读的是联合体，而不是 tag 选中的那份载荷；而 `impl Ord` 之类的实现会要求**每个**载荷都满足同一组约束，不点名就生成不了 | `derives = [Clone, PartialEq, Eq, PartialOrd, Ord, Hash, StableHash];`（`Clone` 同时写 `TryClone`；`StableHash` 让这个枚举能直接做 `insert_stable` 的键）；默认值用 `default = Variant;`，那个变体不能带载荷 |
| 没有命名变体字段 | 生成的载荷结构体需要名字，而 `macro_rules!` 不能把一个标识符拼进另一个 | 用元组写法，视图里的字段是位置（`payload.0`、`payload.1`） |
| `Eq` 必须与 `Ord` 一起点名 | 相等是全集关系，这取决于载荷类型；宏唯一能交给编译器核对的性质是那个载荷的有序性 | 只写 `Eq` 不写 `Ord` 会被拒绝（含 `compile_fail` 用例）；载荷确实自等但无序时自己写 `impl Eq` |
| `PanicFallback` 需要显式声明 | 没有"无答案"的变体可自动选择 | `stable_enum_fallback!(Name => Variant());` |
